# 开发规范

## 1. 开发原则

- 先确认当前生产、验收和影子状态，再修改代码。
- 数据契约、评分含义和板块身份变化必须版本化。
- 缺失、异常、过期和不兼容输入采用失败关闭，不为提高完整度补造数据。
- 生产写操作、D1 迁移、Cloudflare 部署和长期服务变更与代码开发分开批准。
- 保留用户已有未提交修改，不以 reset、checkout 或覆盖方式清理工作树。

## 本地版与线上版同步交付（长期要求）

用户已明确要求：以后每次修改看板功能，都同时更新本地版和线上版，并分别验证，不得只改一边。本要求适用于新增功能、修复、界面、交互、数据接口和评分展示；复用源码不代表两端已实际更新或验收通过。

每次功能交付必须：

1. 检查共享页面及本地／云端适配，保持功能与评分口径一致；必要的环境差异应明确记录，例如本地图表、离线缓存与云端接口。
2. 更新实际运行的本地版：`http://127.0.0.1:5184/`。后台改动需重启服务，验证桌面入口及受影响功能，不能只验证开发端口或静态构建。
3. 更新实际线上版：`https://newsmonitor.pages.dev/`。部署后验证正式地址的受影响功能，不能以本地测试、提交代码或构建成功代替线上验收。
4. 分别核验页面／交互、接口响应、真实数据时间、必要的评分版本及异常／缓存状态；数据链路变化还要核对本地快照与线上已发布版本，解释刷新或发布时差。
5. 在变更记录及 `docs/verification/` 的对应记录中分别写明本地与线上版本／提交、更新时间、验证范围、结果和未完成项。报告完成时明确两端状态。

某端因凭据、网络、授权或服务问题未完成时，应继续完成不受影响的工作，明确说明阻碍与下一步，并将整体标为尚未完成双端交付；不得默默略过，也不得用另一端成功替代。用户已有授权继续有效，不重复逐项请示；确需新的授权或登录时再请求用户参与。

功能同步不要求两端每一刻显示相同数据：直连、缓存和发布存在时差，但真实时间、来源、版本及差异必须可解释，不得伪造同步。

纯文档修改只需核验文档与链接，不为此重启服务或重新部署页面。

## 2. 环境准备

```bash
npm ci
python3 --version
node --version
```

本地前端：

```bash
npm run dev
```

Vite 默认只提供前端开发环境及现有代理。需要真实 Pages Functions 时，先构建，再使用受控的 Wrangler 本地环境；不要把生产令牌写入命令、配置或日志。

## 3. 分支与工作树

- `main` 对应可发布基线，不直接进行未验证开发。
- 功能分支建议使用 `codex/<topic>` 或清晰的功能名称。
- 长期 LaunchAgent 必须指向稳定 checkout；`.codex/worktrees/` 仅用于开发。
- 一个分支只解决一个相对完整的问题，避免把无关格式化和功能修改混在一起。
- 合并前同步目标分支并重新运行完整验证。

## 4. 开发步骤

1. 阅读 [项目状态](STATUS.md)、相关架构和现有验证记录。
2. 对多步骤功能编写设计和实施计划；简单修复至少写清验收条件。
3. 先添加能失败的测试，再实现最小修复或功能。
4. 运行局部测试，随后运行完整测试。
5. 更新 README、当前文档、状态页和变更记录中受影响的部分。
6. 检查 diff，确认没有凭据、原始数据、临时文件或无关修改。
7. 提交后通过 Pull Request 审查；部署与迁移另行执行。

## 5. 测试矩阵

### Python 数据生产者

```bash
PYTHONDONTWRITEBYTECODE=1 python3 -m unittest discover -s tools/market_dashboard/tests -v
```

覆盖数据源解析、缺失与单位、评分、概念选择、板块轮动、状态、调度、发布和运维安全。

### 前端、模型和 Functions

```bash
npm test
```

测试使用 Node 内置 test runner，覆盖新闻策略、债务模型、市场模型、API、Functions、板块组件和验收隔离。

### TypeScript 与生产构建

```bash
npm run build
```

该命令先执行 `vue-tsc -b`，再执行 Vite 生产构建。

### 验收构建

```bash
npm run build:acceptance
```

验收构建只能包含合成验收适配器，必须保留测试数据横幅和 `noindex,nofollow`，并且不能请求生产 API。

### 文档和 diff

```bash
git diff --check
```

此外应检查所有 Markdown 相对链接均指向存在的文件或目录。外部 URL 的在线可用性不由离线测试保证。

## 6. 数据源开发

- 新字段必须保存供应商返回的单位和观测时间。
- 先验证身份集合，再按代码映射；不要依赖返回顺序或中文名称。
- 新供应商接入必须声明 `sourceMode` 和失败策略。
- 跨供应商映射必须版本化并人工审核。
- 探针默认只输出白名单元数据；全量或高成本调用必须使用显式参数。
- 测试夹具应最小化并脱敏，不保存授权头或完整原始响应。

数据源职责和切换门禁见 [数据源策略](DATA_SOURCES.md)。

## 7. 契约与数据库修改

修改 payload 或 D1 schema 时必须同时检查：

1. Python 生产者和版本常量；
2. `functions/_lib/market-dashboard.js` 校验；
3. D1 migration 和查询；
4. 前端类型、API 解析和模型；
5. Node 与 Python 测试；
6. 当前文档和 CHANGELOG。

已应用的 migration 不原地修改；新增编号迁移。生产迁移执行前应在 Preview 或独立数据库验证，并准备兼容读取与回滚方案。

## 8. 提交与变更记录

提交信息沿用项目现有风格：

```text
feat: add ...
fix: prevent ...
test: verify ...
docs: document ...
ops: configure ...
```

`CHANGELOG.md` 记录用户可见功能、重要可靠性变化、迁移和验证结果，不逐条复制提交历史。未发布内容先进入“未发布”，生产发布后再归入日期或版本。

## 9. Pull Request 检查

- 说明用户问题、实现范围和明确非目标。
- 列出数据契约、评分、存储、调度或来源是否变化。
- 提供实际运行的测试命令和结果。
- 区分合成数据验证、只读真实数据验证和生产验证。
- 标明是否需要迁移、Secret、功能开关、LaunchAgent 或部署操作。
- 提供回滚方式；数据和接口变化说明兼容边界。

## 10. 发布前门禁

代码合并不等于生产发布。发布前至少确认：

- 所有测试和生产构建通过；
- 目标提交与评审提交一致；
- Cloudflare Pages 环境、D1 绑定和 Secret 正确；
- migration 已在非生产环境验证；
- 生产与验收构建没有混用；
- 数据源额度、时延和来源时间满足目标；
- 最新运行手册和状态页已经更新；
- 用户明确批准迁移、部署和功能开关。

具体操作命令和故障处理见 [运行手册](market-dashboard-operations.md)。

## 11. 文档维护规则

- 架构或运行边界改变：更新 `ARCHITECTURE.md`。
- 新增、移动或删除重要目录：更新 `PROJECT_STRUCTURE.md`。
- 来源、字段、刷新频率或切换策略改变：更新 `DATA_SOURCES.md`。
- 生产／验收状态或验证结论改变：更新 `STATUS.md` 及日期。
- 用户可见变化：更新 `CHANGELOG.md`。
- 快速开始或导航改变：更新 README。
- 历史设计、计划和验证记录保持原始结论，不覆盖成新状态。
