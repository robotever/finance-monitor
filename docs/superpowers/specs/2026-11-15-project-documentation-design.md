# NewsMonitor 项目文档体系设计

## 目的

随着 NewsMonitor 从新闻聚合页扩展为市场研究首页、概念雷达和板块轮动系统，需要一套能回答“项目是什么、代码在哪里、数据怎样流动、当前上线了什么、怎样安全修改”的文档体系。

## 目标

- README 作为入口，不再承载全部实现细节。
- 架构、目录、数据源、开发流程、运行状态分别有唯一权威文档。
- 生产版、验收版、影子版和规划项必须明确区分。
- 变更记录面向用户可见能力和重要工程变化，不复制 Git 提交列表。
- 已有设计稿、实施计划、验证记录和运行手册继续作为证据档案。

## 非目标

- 本轮不重构代码目录、不改变数据源、不部署、不迁移数据库。
- 不把密钥、供应商原始响应、本机私有路径或运行状态文件写入仓库。
- 不为尚未完成的妙想切换或 v3 生产发布制造“已上线”表述。

## 文档结构

- `README.md`：定位、功能、状态、快速开始、文档导航。
- `docs/ARCHITECTURE.md`：系统边界、数据流、运行时、存储、安全与版本契约。
- `docs/PROJECT_STRUCTURE.md`：目录树、目录职责、常见修改入口。
- `docs/DATA_SOURCES.md`：来源职责、字段覆盖、切换规则、验证状态和成本策略。
- `docs/DEVELOPMENT.md`：开发、测试、分支、提交、发布和文档同步规则。
- `docs/STATUS.md`：截至指定日期的生产、验收、影子和数据验证状态。
- `CHANGELOG.md`：按日期归纳重要变化。
- `CONTRIBUTING.md`：贡献入口，链接到开发规范。

## 方案选择

考虑过三种方案：只扩充 README、建立少量核心文档、建立完整企业级文档门户。只扩充 README 会继续混淆入口与运行细节；企业级门户对当前单人项目过重。采用中间方案：八份职责清晰的核心文档，复用现有运行手册和证据记录。

## 验收标准

- 新参与者从 README 能在两次点击内找到架构、目录、数据源、开发、运维、状态和变更记录。
- 文档中的命令与 `package.json`、Python 模块和 Wrangler 配置一致。
- 相对链接可解析，版本与状态描述不把验收能力误写为生产能力。
- `npm test`、Python 测试、构建和 `git diff --check` 继续通过。
